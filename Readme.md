
# Order-Payment API

## 개요

- 장바구니, 결제, 주문 관련 API
- 회원 여부에 따라 회원, 비회원으로 로직 분기됨
---
## 장바구니
- 기술 스택
  - Redis

### 비회원 장바구니

- Redis에 내역을 저장하고, DB에 따로 저장하지 않음
- 삭제 요청 시 Redis에서 즉시 삭제
- 비회원의 장바구니 데이터 보관 전략
  1. 장바구니 조회 시 TTL 초기화 됨
  2. 비회원에게 제공된 식별 키(UUID)의 쿠키 만료
  3. Redis의 장바구니 데이터 접근 불가
  4. 장바구니 데이터의 TTL 만료로 삭제됨

### 회원 장바구니
- Write-Back 방식 도입
- DB 저장을 기본으로 하되, Redis를 캐시로 사용하여 DB 접근을 최소화
- 기본 CRUD는 Redis에 하되, 주기적으로 DB에 저장(Sync)함

### Redis를 이용한 캐싱 처리 (Write-Back 방식)
- 우선적으로 Redis에 장바구니 데이터를 저장하고, 이후 한꺼번에 DB 동기화
- Dirty Flag 전략을 사용해서 변경 사항에 대해서만 DB 동기화 실행 
  - 장바구니에 변경 사항 발생 시 해당 항목에 Dirty Flag 세움
  - 스케줄러가 주기적으로 `dirty:true`가 붙은 장바구니 키만 조회해서 DB에 일괄 저장
  - Redis 전체를 확인하지 않고 변경 사항에 대해서만 Sync함

## 주문
- 기술 스택
  - RabbitMQ
### MSA 구조로 인한 분산 트랜잭션 문제 발생
- Microservice Architecture(MSA)를 기본 개발 방식으로 도입
- 여러 API가 분할되어 서비스되고, 각각 다른 DB에 데이터가 저장됨 (`Book API`, `User API`, `Cou.pon .API` etc.)
- 그에 따른 데이터 정합성을 보장해야하는 분산 트랜잭션 문제가 발생함
### 분산 트랜잭션을 위한 Saga 패턴 도입
- 해당 문제를 해결하기 위해 Saga 패턴을 도입
- Choreography 방식과 Orchestration 방식 중 어떤 방식을 도입할지 고민하게 됨

### 1. Choreography 방식
- **성공 메커니즘**
  1. `Order API`가 주문 이벤트 발생시키고 다음 서비스(`Book API`) 로 전송함 (Saga 시작)
  2. 이벤트를 수신받은 서비스(`Book API`)는 각자의 로직(재고 차감)을 수행하고 다음 서비스(`User API`)에 이벤트를 전송함
  3. `Book API`, `User API`, `Coupon API`순서로 이벤트를 전달받고 로직 수행함
  4. 마지막으로 성공 이벤트를 `Order API`에서 수신 받으면 주문 Saga 종료됨
- **실패 메커니즘** 
  1. 한 서비스에서 비즈니스 로직 실패 (ex. 재고 부족)
  2. 해당 서비스는 실패 이벤트 발행 후 Order API에 실패 메세지 전송 
  3. Order API는 클라이언트에 실패 응답
  4. 문제가 발생한 서비스로부터 `Order API`까지 역순으로 보상 트랜잭션이 시작

- **해당 방식의 장점** 
  - `Order API`측에서는 이벤트 발행과 Saga 시작만 하면 되기 때문에 `Order`로직이 비교적 단순함
  - 다음 서비스를 몰라도 되기 때문에 느슨한 결합을 유지할 수 있음
- **해당 방식의 단점**
  - 직접적인 관리 주체가 없기 때문에 현재 주문이 어떤 상태인지 관리하기 매우 어려움
  - 각 서비스에서 실패 이벤트 발행과, 실패 트랜잭션 시작 로직도 포함하고 있어야 하기 때문에 로직이 길고 복잡해짐
  - 유지 보수, 디버깅이 어려움
  - 순환 참조의 문제가 발생할 수 있음

### 2. Orchestration 방식
- **성공 매커니즘**
  - `Order API` 가 Orchestrator가 되어 주문 Saga의 모든 흐름과 상태를 관리함
  - 각 서비스에 이벤트를 전송하고, 응답을 받음
  - 성공 응답이 반환될 경우, 상태를 업데이트하고 다음 서비스에 이벤트 전송
  - 마지막 서비스로부터 성공 응답을 받을 경우 주문 Saga 종료
- **실패 매커니즘**
  - 특정 서비스에서 비즈니스 오류 발생 (ex. 재고 부족), 자체적으로 롤백 후 `Order API`에게 실패 메세지 전송
  - `Order API`가 비즈니스 오류가 발생한 서비스로부터 실패 메세지를 수신받음
  - 보상 이벤트를 발행하고 그 이전 서비스부터 순차적으로 보상 트랜잭션을 시작함

- **해당 방식의 장점**
  - 주문 Saga를 Orchestrator(`Order API`)가 직접 관리하기 때문에 상태 파악과 오류 원인을 쉽게 파악할 수 있음
  - 유지보수가 Choreography 방식에 비해 간편함
  - 순환 참조 문제 방지
- **해당 방식의 단점**
  - Orchestrator가 많은 로직을 떠안게 되어 무거워짐

### Orchestration 방식 선정
> 개발하고자 하는 서비스(주문, 결제)는 단계적으로 로직이 실행되어야 하고, 트랜잭션의 가시성이 중요하므로 **Orchestration** 방식으로 선정함

### 정합성과 멱등성 보장을 위한 Outbox 패턴과 Deduplication Log 도입 
- **문제점**
  - 각 서비스에서 실행되는 비즈니스 로직(ex. 재고 차감 후 DB 저장)과 응답 이벤트 전송 로직은 같은 트랜잭션으로 묶일 수 없음
  - 만약 비즈니스 로직은 성공했지만, 메세지 전송에 실패할 경우, 각 서비스의 **데이터 정합성**이 깨잘 가능성이 있음 
  - 데이터 정합성을 보장하기 위해 적어도 한번 (`At-least-once delivery`) 전송됨을 보장해야함
- **Outbox 메커니즘**
  1. 비즈니스 로직 이후 바로 전송되는 것이 아니라 Outbox 테이블에 저장(save)됨 
     - 비즈니스 로직과 Outbox에 저장되는 로직은 한 트랜잭션으로 묶이게 됨
  2. Outbox에 저장된 이후 (트랜잭션이 커밋된 이후) 즉시 Outbox 테이블을 읽어 전송되지 않은 메세지를 전송함 
  3. 만약 전송 실패 시, 스케줄러에 의해 전송되지 않은 메세지를 전송함
  4. 적어도 한번 (`At-least-once delivery`) 전송됨을 보장
- (추가) **멱등성 보장**을 위한 `Deduplication Log`의 도입
  - Outbox는 '적어도 한번 전송'은 보장하지만 '두번 이상 전송'이 발생할 가능성을 가지고 있음
  - 요청이 두번 전송되게 되면 로직이 두번 수행되는 **멱등성 위반**이 발생함
  - 이것을 방지하기 위해 각 서비스별로 `Deduplication Log` 테이블을 두고, 요청마다 Log를 기록하여 중복 요청시 무시하도록 함
